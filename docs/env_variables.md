# Adding Environment Variables and Secrets

Local configuration is built by `quickstart.sh`:

| File                              | Committed? | Purpose                                                                                      |
|-----------------------------------| ---------- |----------------------------------------------------------------------------------------------|
| `.env.example`                    | Yes        | The **public LibreChat** example. Keep it as a clone from upstream. Don't make changes here. |
| `.env.deloitte`                   | Yes        | Our `.env` template: every non-secret value, plus blank secret keys.                         |
| `.secrets/.shared-secrets`        | **No**     | Secrets everyone on the team uses the same value for.                                        |
| `.secrets/.personal-secrets`      | **No**     | Secrets that are specific to you (for example your ID token).                                |
| `.secrets/.shared-secrets.example` | Yes       | The list of required **shared** secret key names (no values).                                |
| `.secrets/.personal-secrets.example` | Yes     | The list of required **personal** secret key names (no values).                              |
| `.env`                            | **No**     | Generated by `quickstart.sh` from the files above. Don't edit by hand.                       |

## Steps

### 1. Check whether the variable exists in `.env.example`

`.env.example` comes from the public LibreChat repo, so it is the source of truth for upstream variables and their documentation.

```zsh
grep -n "MY_NEW_VARIABLE" .env.example
```

Also check for a commented-out version (`# MY_NEW_VARIABLE=`).

### 2. Add it to `.env.deloitte`

- **If it exists in `.env.example`:** copy the entry, including its explanatory comments, across to `.env.deloitte`, and set our value.
- **If it does not exist:** add it **only** to `.env.deloitte`, with a short comment explaining what it does. Do not add Deloitte-only variables to `.env.example`, so it stays easy to merge from upstream.

Keep optional or unused variables commented out (`# KEY=value`).

### 3. If the value is a secret, move it to a secrets file

A value is a **secret** if knowing it lets someone act as you or the app: API keys, client secrets, session and signing secrets, encryption keys, private keys and tokens. 

Client IDs, tenant IDs, Agent IDs, URLs, scopes and feature flags are **not** secrets: they stay in `.env.deloitte`.

1. In `.env.deloitte`, leave the key blank and add the comment used by the other secrets:

   ```
   # Populated from .secrets/.shared-secrets by quickstart.sh
   MY_NEW_SECRET=
   ```

   Use `.secrets/.personal-secrets` in the comment for a personal secret.

2. Choose the file:
   - **Shared secret:** the same value for everyone. Add the key to `.secrets/.shared-secrets`.
   - **Personal secret:** differs per developer, or is tied to your identity. Add the key to `.secrets/.personal-secrets`.

3. Add the **key name only** (no value) to the matching template, `.secrets/.shared-secrets.example` or `.secrets/.personal-secrets.example`, and add `KEY=value` to your own real file. Keep both files alphabetical.

4. Never put a secret value in `.env.deloitte`, `.env.example` or any committed file.

### 4. Tell other people about the new secret

- **Shared secret:** send the updated `.secrets/.shared-secrets` (or just the new line) to the team over a secure channel. Do not paste it in tickets, PRs or chat channels. Everyone needs it, because `quickstart.sh` stops if any key in the `.example` file is missing or empty. Check that your file has the same number of lines as the example:

  ```zsh
  wc -l .secrets/.shared-secrets .secrets/.shared-secrets.example
  ```

- **Personal secret:** share only how to get one (for example a link or the steps to generate it), and update `deloitte/README.md` (Quickstart) if it changes the setup steps. Everyone adds their own value to `.secrets/.personal-secrets`.

### 5. Confirm `quickstart.sh` still works

`quickstart.sh` copies `.env.deloitte` to `.env`, fills every key listed in the two `.example` files, sets the hostname-based URLs, and starts the containers. After your change, run it and check:

```zsh
./quickstart.sh "<YOUR_TOKEN_HERE>"
```

- It completes without a "Missing secrets in …" error.
- The new key is present with the right value in the generated `.env` (check the key and length, not the value: `grep -c "^MY_NEW_SECRET=." .env`).
- The `api` container starts and the app is reachable at the printed link.

`quickstart.sh` only writes the three token keys (`ANTHROPIC_API_KEY`, `LLM_GATEWAY_LOCAL_IDENTITY_TOKEN_SESSION`, `RAG_OPENAI_API_KEY`) into `.secrets/.personal-secrets` itself. Any other new personal secret must be added to that file by hand before the script will pass validation. If your new variable should also be set by the script (like the hostname URLs), update `quickstart.sh` and the Quickstart section of `deloitte/README.md`.

## Deployed environments

These steps cover **local** development only. Deployed environments read their configuration from `charts/values-*.yaml` (non-secret values) and the Key Vault or chart secrets (secret values). If the new variable is needed there, update those files too.
