# Eval Framework Architecture

Reference document for the MyAssist skill evaluation framework. Update this file as the framework evolves.

---

## Overview

A config-driven, adapter-agnostic framework for testing agent skills end-to-end using [DeepEval](https://github.com/confident-ai/deepeval) as the LLM-judge backend. Each skill defines its own `eval_cases.yaml`; all shared orchestration, metrics, and reporting live in `evals/_eval/`.

Scores are averaged across N runs to account for LLM non-determinism. Results are persisted locally and optionally exported to Langfuse for experiment tracking.

## Core Components

### `runner.py` — Orchestration Engine

The central loop. For each case:

1. Loads config and case from YAML (via `loader.py`)
2. Dynamically imports and instantiates the adapter
3. Builds an `EvaluatorModel` (LLM-as-judge bridge to DeepEval)
4. Runs the agent N times, collecting `AgentResponse` objects
5. Evaluates two-phase metrics per run
6. Aggregates scores across runs
7. Prints report + saves results to `.results/`
8. Optionally exports OTel traces to Langfuse

### `schema.py` — Config Validation

Pydantic models for `eval_cases.yaml`. Validates on load — bad metrics, mismatched thresholds, missing required fields, or invalid case keys (`case_<n>`) all fail fast with path-aware errors.

Key models: `EvalCasesFile`, `EvalCase`, `Turn`, `TurnAssertion` (discriminated union), `LeadingQuestionProbe`.

### `metrics.py` — Metric Definitions

- `EvaluatorModel` — bridges any LLM callable to DeepEval's judge interface
- `_metric_registry()` — maps metric key strings to DeepEval metric factories
- `_conversational_metric_registry()` — conversational metric factories (multi-turn only)
- `evaluate_turn_assertions()` — per-turn deterministic + LLM-judged checks
- `build_metrics()`, `build_conversational_from_keys()`, `build_leading_question_probes()` — instantiation helpers

### `adapters/base.py` — Adapter Contract

Abstract base class every agent framework adapter must implement:

```python
class AgentAdapter(ABC):
    def invoke_text(self, query: str, context: str) -> AgentResponse: ...
    def invoke_file(self, query: str, file_paths: List[Path]) -> AgentResponse: ...
    def invoke_sequential(self, turns: List[dict], source_text=None) -> List[AgentResponse]: ...
    def get_agent_metadata(self) -> dict: ...  # optional override
```

`AgentResponse` carries: `content` (str), `tools_called` (List[ToolCallRecord]), `retrieval_context` (List[str] — RAG chunks returned by `include_retrieval`, empty for non-RAG agents), `raw` (optional).

## Evaluation Flow

### Single-Turn (`invoke_text` / `invoke_file`)

```
For each run (N times):
  1. Call adapter.invoke(method, ...)  →  AgentResponse
  2. Build LLMTestCase (input, actual_output, context, expected_tools)
  3. Phase 1 — Gating metrics         (failures block after averaging)
  4. Phase 2 — Diagnostic metrics     (reported, never block)
  5. Evaluate leading question probes (gating or diagnostic per type)

After N runs:
  Average all scores → aggregate_results()
  Raise AssertionError if any gating metric avg < threshold
```

### Multi-Turn (`invoke_sequential`)

```
For each run (N times):
  1. Send turns sequentially via adapter (each turn sees full history)
  2. Per-turn assertions (deterministic + LLM-judged, printed live)
  3. Build ConversationalTestCase from full turn history
  4. Evaluate session-level conversational metrics
  5. Evaluate standard gating/diagnostic metrics on the FINAL turn only
  6. Evaluate case-level leading question probes on the final turn

After N runs:
  Aggregate all scores, raise if gating failed
```

## Metrics

### Standard (Single-turn and Multi-turn)

| Key | Phase | Description |
|---|---|---|
| `hallucination` | Gating | Detects fabricated information not in source |
| `task_completion` | Gating | Whether the task was fulfilled (single-turn only) |
| `tool_correctness` | Gating | Verifies correct tools were called |
| `role_consistency` | Gating | Agent maintained expected persona |
| `instruction_adherence` | Gating | Followed format and constraint instructions |
| `policy_compliance` | Gating | Deterministic disclaimer/policy check |
| `faithfulness` | Diagnostic | Groundedness in source material or retrieved context |
| `answer_relevancy` | Diagnostic | Relevance of response to query |
| `summarization` | Diagnostic | Quality of summarisation |
| `contextual_recall` | Diagnostic | Coverage of retrieved context vs. expected output (RAG) |
| `contextual_precision` | Diagnostic | Signal-to-noise ratio of retrieved chunks (RAG) |
| `contextual_relevancy` | Diagnostic only | Relevance of retrieved chunks to the query (RAG) — judge must output per-chunk JSON; use as diagnostic, not gating |
| `bias` | Diagnostic | Detects biased language |
| `toxicity` | Diagnostic | Detects harmful content |

### Conversational (Multi-turn only, `invoke_sequential`)

| Key | Description |
|---|---|
| `conversation_completeness` | All user requests addressed across turns (replaces `task_completion` for multi-turn) |
| `conversational_role_consistency` | Consistent persona across the conversation |
| `conversational_instruction_adherence` | Instructions followed throughout the session |

### Turn Assertion Types

Evaluated per-turn, printed live during execution:

| Type | Evaluation | Description |
|---|---|---|
| `expected_tools` | Deterministic | All expected tool names appear in `tools_called` |
| `contains_any` | Deterministic | Response contains at least one of the listed phrases |
| `not_contains` | Deterministic | Response contains none of the listed phrases |
| `leading_question` | LLM-judged (GEval) | Yes/no question evaluated against the turn's response |

## `eval_cases.yaml` Schema

```yaml
adapter: _eval.adapters.librechat_adapter.LibreChatAdapter
agent_id: ${MY_AGENT_ID}            # optional — overrides LIBRECHAT_AGENT_ID env var; use ${VAR} refs, never literal IDs
invoke_method: invoke_text          # invoke_text | invoke_file | invoke_sequential
num_runs: 3

cases:
  case_1:                           # Keys must match case_<n>
    name: "Human-readable description"
    category: "Content Generation & Transformation"
    invoke_method: invoke_sequential  # per-case override
    source_material: "documents/sample.md"    # omit for KB-backed RAG — agent retrieves its own context
    chatbot_role: "A meeting summarisation analyst"
    user_query: >-                  # for invoke_text / invoke_file
      <user prompt>
    expected_output: >-
      <structural description of correct output>
    expected_tools:
      - name: skill
        input_parameters:
          skillName: "meeting-summariser"

    turns:                          # for invoke_sequential
      - content: "First user message"
        attach_source: true
        turn_assertions:
          - type: expected_tools
            name: "Skill tool called"
            tools:
              - name: skill
                input_parameters:
                  skillName: "meeting-summariser"
          - type: contains_any
            name: "Has action items"
            phrases: ["action item", "action items"]
          - type: leading_question
            name: "Asks for detail level"
            question: "Does the response ask the user to choose a detail level?"
      - content: "Brief"
        turn_assertions:
          - type: leading_question
            name: "Has structured summary"
            question: "Does the response contain a structured summary?"

    metrics:
      - hallucination
      - faithfulness
      - conversation_completeness   # use this instead of task_completion for multi-turn
    thresholds:
      hallucination: 0.5
      faithfulness: 0.5
      conversation_completeness: 0.5

    diagnostic_metrics:
      - answer_relevancy
    diagnostic_thresholds:
      answer_relevancy: 0.5

    leading_questions:
      - name: "Structural Template"
        type: gating                # gating = blocks; diagnostic = non-blocking (default)
        threshold: 0.5
        question: "Does the summary follow the standard structure?"
      - name: "Conciseness"
        question: "Is the summary concise?"
```

## Adapters

### Current: `LibreChatAdapter`

Calls LibreChat's agent endpoint (`/api/agents/v1/chat/completions`) via raw `httpx` (not the OpenAI SDK) so that the full response body is accessible.

Always sends `include_retrieval: true`. For agents with a knowledge base, the response includes a `retrieval.sources` array; the adapter maps each source's `content` field into `AgentResponse.retrieval_context`. For non-RAG agents the field is an empty list.

The runner passes `retrieval_context` to `LLMTestCase` so RAG metrics (`contextual_recall`, `contextual_precision`, `contextual_relevancy`) have real retrieved chunks to evaluate against. For non-RAG cases with `source_material`, the runner falls back to `[source_material]` for `retrieval_context`.

Required env vars:
- `LIBRECHAT_BASE_URL`
- `LIBRECHAT_API_KEY`
- `LIBRECHAT_AGENT_ID`

### Adding a New Adapter

Implement `AgentAdapter` from `_eval/adapters/base.py` and set `adapter:` in the YAML to the dotted module path:

```python
class MyAdapter(AgentAdapter):
    def invoke_text(self, query, context) -> AgentResponse: ...
    def invoke_file(self, query, file_paths) -> AgentResponse: ...
    def invoke_sequential(self, turns, source_text=None) -> List[AgentResponse]: ...
```

```yaml
adapter: _eval.adapters.my_adapter.MyAdapter
```

## CLI Reference

```bash
# Run all cases
uv run eval-run --config "evals/skills/<Skill Name>/eval_cases.yaml"

# Run specific cases
uv run eval-run --config <path> --case case_1 case_2

# Override run count
uv run eval-run --config <path> --num-runs 5

# Override gating metrics
uv run eval-run --config <path> --metrics hallucination,task_completion

# Export to Langfuse
uv run eval-run --config <path> --langfuse --run-name "baseline"

# Sync cases to Langfuse Dataset (compile + push)
uv run eval-run --config <path> --sync-dataset

# View results
uv run eval-summary --config <path>
uv run eval-summary --config <path> --latest
uv run eval-summary --file <path/to/case_1.json>
```

## Langfuse Integration

All telemetry flows through OpenTelemetry to Langfuse's native OTLP endpoint.

### Experiment tracking workflow

```bash
# 1. Compile YAML and upload cases as dataset items (idempotent)
uv run eval-run --config <path> --sync-dataset

# 2. Run baseline
uv run eval-run --config <path> --langfuse --run-name "baseline"

# 3. Make changes, run again
uv run eval-run --config <path> --langfuse --run-name "v2-improved-prompt"
```

Each trace carries: case key/name, run name, run count, gating verdict, per-metric scores. Two Langfuse scores are posted per trace: `eval_score` (0–1 mean of gating metrics) and `passed` (bool).

### Environment variables

| Variable | Purpose |
|---|---|
| `EVAL_LANGFUSE_BASE_URL` | Langfuse instance URL (default: `http://localhost:3000`) |
| `LANGFUSE_BASE_URL` | Fallback if above not set |
| `LANGFUSE_PUBLIC_KEY` | Used to build OTLP auth header |
| `LANGFUSE_SECRET_KEY` | Used to build OTLP auth header |
| `EVAL_PUSH_LANGFUSE=1` | Enable Langfuse globally without `--langfuse` flag |

## Onboarding a New Skill

### Option A — Scaffolder (recommended)

Invoke the eval-scaffolder skill. It:
1. Reads the skill's `SKILL.md`
2. Asks for a sample query, input document, and expected output
3. Classifies the skill into a category, reads the matching template and the Meeting Summariser worked example
4. Generates `eval_cases.yaml` (8 cases × 4 documents) and 4 sample documents
5. Automatically runs `--sync-dataset` and a baseline eval

### Option B — Manual

1. Copy a template from `evals/_eval/templates/` matching the skill's category
2. Create `evals/skills/<Skill Name>/eval_cases.yaml` and `documents/`
3. Write 8 cases (2 per doc — one `invoke_text`, one `invoke_sequential`)
4. Run `uv run eval-run --sync-dataset --config <path>` to validate and upload

## Importing Real-World Cases (Dataset Importer)

The dataset-importer skill converts curated Langfuse dataset items (from real traces, UAT feedback, or Q&A pairs) into `eval_cases.yaml` entries.

**Flow:**
1. Fetches only user-added items (skips items synced by `--sync-dataset`)
2. Detects item format (traced session, UAT trace, curated Q&A, scored trace)
3. Extracts real user turns (filtering injected skill instructions and tool_call messages)
4. Pairs each turn with its expected assistant response to derive `turn_assertions`
5. Selects metrics per-case using `REFERENCE.md` tables
6. Appends cases to `eval_cases.yaml` with sequential `case_N` keys

UAT failures become gating `leading_question` probes at threshold `0.8`.
